• 我建议按 “主数据集 + 从数据集” 来设计：

  主数据集: 原来的 LeRobotV3，负责 img + lowdim + action + episode/window sampling
  从数据集: FT LeRobotV3，只按 timestamp 被查询，不决定训练窗口

  也就是训练样本的 idx / horizon / n_obs_steps / action 仍然由原来的 hirol_lerobot_v3_dataset.py 决定。FT 只根据当前 obs 图像的 timestamp 去主数据集对应
  episode 里查一段 FT。

  我更推荐 causal trailing window，比 manipforce 里“两张图之间的 FT”更稳：

  对每个 obs image timestamp t_img:
    取 FT timestamp in (t_img - ft_window_sec, t_img]
    固定成 K 帧

  比如：

  ft_window_sec: 0.05   # 50ms
  ft_steps: 10          # 如果 FT 200Hz，50ms 大约 10 帧

  返回 batch 可以是：

  obs["ft_data"].shape = [B, n_obs_steps, ft_steps, ft_dim]

  或者如果现有模型只接受 lowdim 向量，可以先 flatten 成：

  obs["ft_data"].shape = [B, n_obs_steps, ft_steps * ft_dim]

  但长期看保留 [To, K, D] 更清晰，后面可以单独做 FT encoder。

  关键点：

  1. 不要让 FT 决定 dataloader 的主 index
     主 index 应该还是 image/action 那条 timeline。否则 action horizon、obs image、lowdim 都会被 FT 高频率打乱。
  2. 只在同一个 episode 内 searchsorted
     初始化时把 FT dataset 的每个 episode 拆成：

  ft_episode_timestamps[episode_idx]
  ft_episode_data[episode_idx]

  然后每次 sample 根据主数据集的 episode_idx 查对应 FT episode。不要全局 search，否则 episode 边界附近可能错配。

  3. 避免未来信息泄漏
     对训练 obs 来说，FT window 最好只取 <= t_img 的数据。
     manipforce 里 episode 第一帧用 [current, next] 会包含未来 FT，这对严格因果策略不太理想。你的场景我建议统一用 trailing window。
  4. 固定 FT 帧数
     FT 采样率可能抖动，所以 search 出来的数量不一定等于 K。处理方式：

  少于 K: 用最早/最后一帧 pad，或者全 0 + mask
  多于 K: linspace 下采样，或者插值到 K 个时间点
  空窗口: 全 0，并附带 valid mask

  我建议同时返回：

  obs["ft_data"]      # [B, To, K, D]
  obs["ft_mask"]      # [B, To, K]
  obs["ft_timestamps"] 可选，仅 debug 用

  5. 时间戳要确认同源时钟
     如果两个 LeRobotV3 数据集的 timestamp 来自同一台机器同一个 clock，直接对齐可以。
     如果 FT 单独设备记录，可能需要每个 episode 一个 offset：

  t_ft_aligned = t_ft + episode_offset

  否则 searchsorted 逻辑对了，结果也可能整体偏几十毫秒。
